# 售前技术演示方案优化 · 集成中台

> 适用对象：售前工程师、技术方案负责人、参与客户演示的研发同学
> 配套材料：`产品介绍-集成中台.html`（21 页演示稿，可直接投屏）

## 一、先诊断：为什么"技术讲得很清楚"却推不动

技术演示失败，极少是因为技术讲错了。多数是下面五个问题：

| # | 反模式 | 客户的真实感受 | 修正方向 |
|---|---|---|---|
| 1 | 从登录页开始，按菜单顺序走一遍 | "这是产品培训，不是解决我的问题" | 从**客户的问题**开始，产品只在证明结论时出现 |
| 2 | 只演示顺利路径 | "生产环境不会这么顺，你们没做过真实的项目" | **刻意制造一次失败并现场恢复** |
| 3 | 大段展示配置项与参数 | "功能很多，但和我有什么关系" | 每个配置项必须挂一个**业务后果** |
| 4 | 90 分钟讲 20 个功能 | "记不住，也不知道重点" | 45 分钟内讲透 **3 件事** |
| 5 | 结尾问"还有什么问题吗" | 会议自然结束，没有下一步 | 结尾**给一个具体的下一步和时间点** |

**核心判断标准**：演示结束后，客户能不能用一句话向他的老板复述你的价值。如果不能，这次演示没有产生资产。

## 二、演示叙事结构：Impact-First 四段式

不要按产品模块组织，按客户的认知顺序组织。

```
① 量化问题  →  ② 展示结果  →  ③ 回推实现  →  ④ 给出证据
   （他们的痛）   （他们得到什么）  （怎么做到的）   （谁验证过）
```

**① 量化问题**——用客户的数字，不用行业的数字
> "你刚才提到目前有 8 个系统需要互相同步。如果是两两直连，这是 28 条链路；每新增一个系统，要新增 8 条链路并重测 8 个对接方。我们今天想验证的是：能不能让新增系统只增加 1 次接入。"

**② 展示结果**——先给终态，再讲过程
> 先打开**执行记录**和**仪表盘**，让客户看到一条已经跑完的同步链路和它的结果行数。不要先讲怎么配的。

**③ 回推实现**——此时客户开始有"想要"的动机，才讲配置与架构
> 回到数据源登记、字段映射、调度设置。这时候他是在**验证可行性**，不是在忍受功能清单。

**④ 给出证据**——用截图、审计记录、指标接口收尾
> 打开字段变更审计，展示"谁在什么时候改了哪个字段"；打开 Prometheus 指标，说明可以接入客户现有监控。

## 三、三个 Aha Moment：本产品最该被记住的三件事

每个演示至少要有一次客户明显前倾（"这个正好是我们需要的"）。本产品有三个天然的高光点，按场景选一到两个重点做：

### Aha #1 · 死信人工决裁（最强差异化）

**为什么强**：几乎所有同类方案都能"同步成功"，但很少能回答"同步失败之后怎么办"。这是客户的真实痛点，也是竞品最容易含糊过去的地方。

**怎么做**：
1. 提前准备一条脏数据（例如必填字段为空、手机号格式非法）
2. 触发任务 → 明确告知："这条会失败，我们看一下系统的处理方式"
3. 执行记录里定位失败步骤
4. 打开死信列表 → 展示脱敏后的滞留数据
5. **现场修正字段 → 重新落库** → 回到执行记录看到补数成功

**收尾话术**：
> "刚才这条数据如果发生在手工方案里，它就在某个日志文件里，需要有人发现、判断、手写 SQL 补进去。这里的差别不是效率，是**你有没有能力在没有人盯着的情况下承载核心数据**。"

### Aha #2 · 换一个数据源，只是换一张表单

**为什么强**：直接击中"每接一个系统就要排期开发"这个成本源头。

**怎么做**：
1. 先用 HTTP API 类型登记一个数据源，演示探测与预览
2. 切到 MySQL，再走一遍同样的流程
3. 强调：登记、测连、探测表结构、配映射、调度的**流程完全一致**，团队只需要学一次

**关键加强点**：如果客户提到国产数据库（达梦 / 人大金仓）或消息队列（Kafka / RocketMQ），当场指出这些已在连接器目录内。这比会后发资料有效得多。

**收尾话术**：
> "连接器数量本身不构成优势——长尾连接器谁都能补。真正的差别是**统一的数据源模型**：正因为所有类型共用一套模型，映射、增量、死信、审计这些治理能力才能同时作用在数据库和你那个 HTTP 接口上。"

### Aha #3 · 一把 Key 完成闭环（生态场景必演）

**为什么强**：这是本产品在设计上最有辨识度的定位——集成能力可以**发放**出去，而不只是内部自用。

**怎么做**（用终端，40 秒）：
```bash
# 1. 自助开通沙箱密钥
curl -X POST $BASE/api/open/register -d '{"name":"demo"}'

# 2. 查看能力目录
curl $BASE/api/open/catalog -H "X-Api-Key: ipk_..."

# 3. 触发一次同步
curl -X POST $BASE/api/open/jobs/trigger -H "X-Api-Key: ipk_..." -d '{"jobId":"..."}'

# 4. 查看执行结果
curl $BASE/api/open/executions -H "X-Api-Key: ipk_..."
```

**收尾话术**：
> "你们的合作伙伴接入时，是把这份文档发给他，还是给他一把有 IP 白名单和限流的钥匙？这里省下的不是开发量，是**你每次对接外部团队时的人力投入**。"

### 备用 Aha · 映射预览
如果会议室里有数据工程角色，映射预览（先跑一遍转换、把源字段到目标字段的实际结果摊开确认）往往比死信更能打动人。准备这个路径作为 Plan B。

## 四、分档脚本

时间越短，越要克制。**不要压缩内容，要减少内容。**

### 15 分钟 · 展会 / 高管碰面

| 时间 | 内容 | 页 |
|---|---|---|
| 0–2 | 只问一个问题："你们现在有几个系统要互相同步？一条新链路要多久？" | 05（只讲交付慢 + 故障黑盒两条） |
| 2–8 | **Aha #1 死信人工决裁**（唯一的技术高光） | 11 → 现场死信操作 |
| 8–12 | 架构图，只讲一句："配置替代开发" | 08 |
| 12–15 | 下一步 + 主动说明不做什么 | 21 |

**禁忌**：不要打开数据源列表逐条讲连接器。

### 30 分钟 · 标准技术评估（最常用）

| 时间 | 内容 | 页 |
|---|---|---|
| 0–3 | 问题量化 + 确认听众最关心的两条代价 | 04 → 05 |
| 3–7 | 定位（一句话价值主张）+ 全景架构 | 07 → 08 |
| 7–12 | **Aha #2 换数据源**：登记 → 探测 → 映射预览 | 09 → 10 |
| 12–18 | **Aha #1 死信**：失败 → 定位 → 决裁 → 补数成功 | 11 |
| 18–23 | SSO 与组织同步（按听众角色决定深浅） | 12 → 13 |
| 23–26 | 安全清单——**主动交给对方安全团队** | 16 |
| 26–30 | 落地四步 + POC 提案（当场确认时间点） | 18 → 20 → 21 |

**关键动作**：第 23 分钟把安全清单打印件推到桌子中间。这个动作的心理效果远大于口头承诺"我们很安全"。

### 45 分钟 · 多角色评审（含安全 / 架构）

在 30 分钟版本上扩展：

- 增加 **Aha #3 API Key 闭环**（终端演示，5 分钟）
- 增加**开放服务与资源可见性隔离**（14 页）——多集成商共存的场景
- **现场打开 SAML 配置**，展示 IdP 证书配置项，说明未签名断言会被拒绝
- 增加 **Prometheus 指标接入**演示（15 页）：打开指标接口，说明可以接进客户现有的监控告警
- 留出 5 分钟专门听安全团队提问，**不打断、不辩解**

**注意**：45 分钟是多角色的上限。如果会议排了 60 分钟，把多出来的时间用于 Q&A，不要用来讲更多功能。

## 五、失败演示：为什么必须刻意制造一次

只有成功路径的演示，会让**有经验的技术决策者降低信任**。原因是：他见过太多演示很好、生产翻车的项目。

**执行要点**：

1. **提前说明**——"接下来这条数据我故意让它失败，因为我们想讨论的是失败之后发生什么"
2. **不要慌张**——失败是剧本的一部分，语气要平稳
3. **展示定位过程**——执行记录 → 找到失败步骤 → 看到具体原因
4. **展示恢复过程**——死信 → 修正 → 重新落库 → 执行记录显示成功
5. **给出结论**——"这条链路现在可以无人值守运行，因为异常数据不会消失，它会停在死信区等人处理"

**风险预案**：万一真实环境出现了脚本之外的失败（网络、驱动），**不要掩饰**。直接说"这个不是我预期的失败，我们一起看一下原因"，然后走同样的定位流程。这反而是最有说服力的时刻——证明你对自己的产品足够理解。

## 六、技术发现提问清单

这些问题必须**真的用于设计你的方案**，否则会被听出来是套路。同时它们会自然暴露客户现状里的空白点。

**关于现状规模**
- 现在有几个系统需要互相同步数据？这些链路里有多少是手工写的接口？
- 一条新的同步链路，从提需求到上线通常多久？主要卡在哪一段？

**关于运维现实**
- 同步失败的时候你们怎么知道的？发现之后怎么补数据？
- 有没有出现过"数据不一致但没人察觉"的情况？

**关于身份与组织**
- 员工现在有多少个地方存着账号？离职时谁负责逐个关闭？
- 员工跨系统操作需要重复登录吗？客户体验上有抱怨吗？
- 你们的身份体系走的是 AD 域还是钉钉/企微？安全评审对单点登录的签名校验有硬性要求吗？

**关于外部协作**
- 有没有需要对接外部集成商或合作伙伴的场景？现在是发接口文档，还是发账号？
- 外部接入方的权限边界怎么控制的？

**关于技术栈（同时用于方案设计）**
- 目标库里有国产数据库吗（达梦、人大金仓）？源端有 Oracle 或 SQL Server 吗？
- 有用到 Kafka / RabbitMQ 这类消息中间件吗？
- 数据量级和增量频率大概是什么水平？（用于判断增量水位策略）

**禁用的问题**：任何答案明显是"为了让我们展示某个功能"的问题。如果一个问题你不打算用它的答案，就不要问。

## 七、竞争定位：FIA 框架

对每一类潜在竞争方案建立战卡。**原则：承认对方优势，只讲差异化的实际影响，不贬低对手。**

### 类型 A · 商业 iPaaS 平台

| 层面 | 内容 |
|---|---|
| **Fact** | 功能矩阵完整、连接器生态庞大、有成熟的实施方法论与厂商服务团队。 |
| **Impact** | 对客户来说，这意味着能力强，但同时意味着成本结构与厂商强绑定，且很多能力你实际用不到。 |
| **Act** | 把话题从"谁的连接器多"移到"**谁的能力边界与你的场景对齐**"：私有化部署、按集成商发放密钥的资源隔离、数据与身份/组织一体化、无按调用量计费维度。 |

### 类型 B · 开源 ETL 工具（Airbyte / DataX / SeaTunnel / Kettle 等）

| 层面 | 内容 |
|---|---|
| **Fact** | 免费、社区活跃，纯数据同步场景能力强，社区连接器数量多。 |
| **Impact** | 但它是**同步工具**，不是**集成枢纽**：不含单点登录、不含组织与用户同步、不含对外 API 门面、不含面向集成商的凭证与用量管理，这些需要另外选型再自行集成。 |
| **Act** | 强调定位差异，而不是功能多少。"如果你们只需要库到库的同步，开源方案是合理选择。你们提到还需要跨系统免登和给外部伙伴发接入能力，这部分开源工具不覆盖，需要额外拼接 2–3 个组件并由你们自己承担集成与运维。" |

### 类型 C · 自研脚本 + 定时任务

| 层面 | 内容 |
|---|---|
| **Fact** | 初始投入低，完全可控，贴合现有团队习惯。 |
| **Impact** | 缺乏死信滞留与重放、缺少字段级审计与版本回滚、缺少统一的执行视图。**更大的风险是：写脚本的人一旦流动，没人敢改这些代码。** |
| **Act** | 不要攻击自研。把对话引到**全生命周期成本**："开发成本只是一个部分，更要算上维护、故障发现与恢复、以及知识集中在个人身上的风险。我们可以先针对你们最复杂的那条链路做对比验证。" |

### 类型 D · 低代码 / 流程编排平台

| 层面 | 内容 |
|---|---|
| **Fact** | 编排可视化程度高，业务人员上手快。 |
| **Impact** | 但数据同步的可靠性能力（死信、快照回滚、字段审计、增量水位、防回环）通常不是其设计重点。 |
| **Act** | 用**失败场景**来区分：现场演示死信决裁流程，对比"流程图上显示失败"与"失败数据被安全滞留并可人工决裁"的差别。 |

### 技术层面的三区划分（用于判断把火力放在哪里）

| 区域 | 内容 |
|---|---|
| **Winning（重点打）** | 数据 + 身份 + 组织 + 开放门面的一体化；死信人工决裁；字段级变更审计与快照回滚；私有化部署；面向集成商的密钥资源可见性隔离；"空跑 0 行不算成功"这类防假成功设计 |
| **Battling（转移到 TCO 与运维）** | 连接器数量、调度能力、可观测性——双方都够用，不要在功能点上纠缠，转到实施速度与运维负担 |
| **Losing（诚实承认后重构）** | 极致大规模单表吞吐、变更数据捕获（CDC / binlog 级实时）、超大规模文件批量传输、可视化编排的复杂程度、社区生态的长尾连接器。**这些问题一旦被问到，直接承认没有做，然后给出替代路径与阶段划分，绝不含糊。** |

## 八、高频异议处理

技术异议往往不是字面意思。先解码，再回答。

| 客户说 | 实际在问 | 应对策略 |
|---|---|---|
| "支持 SSO 吗？" | "能过我们的安全评审吗？" | 不要只回答"支持"。把第 16 页安全清单给对方安全团队，现场打开 SAML 的 IdP 证书配置项，解释未签名断言会被拒绝。 |
| "能撑多大的数据量？" | "我们被厂商坑过" | 先反问他现在的量级与增量频率，再说明本产品在同等量级下的策略（水位增量、批量装载），并提议在验证阶段用他们的真实数据校准。**不要给出没有依据的并发数字。** |
| "我们要私有化部署。" | 可能是"安全团队不让上公有云"，也可能是"机房已有沉没成本" | 这两个是完全不同的问题。先问清楚是哪一个，再针对性回应。 |
| "XX 厂商给我们演示过类似的东西。" | 可能是"你能比他更好吗"，也可能是"帮我确认我的判断" | 不要接竞品框架。先回到需求："对方演示的哪一部分最打动你？我们一起看那个场景在你们环境里需要什么条件。" |
| "这块我们打算自己写。" | "不信任外部依赖" 或 "工程团队想要这个项目" | 承认合理性，然后把**建造总成本**摊开：人力投入、持续维护、故障恢复能力、人员变动风险。不要争论技术优劣。 |
| "能实时同步吗？要做 CDC。" | 对延迟敏感，或已被灌输了"实时=先进" | **直接说明目前不支持 binlog 级捕获**，增量基于水位线。然后问他真实的延迟要求：如果是分钟级要求，水位增量完全覆盖；如果确实需要秒级，明确放到第二阶段评估。 |
| "功能太多了，我们其实只要数据同步。" | 采购侧希望方案简单、预算可控 | 说明能力是模块化的，不需要的能力不产生额外配置负担，也不存在按功能计费的叠加。**这一条要说清楚，否则"一体化"会变成负担的联想。** |
| "价格怎么样？" | 通常是在评估推进的必要性 | 技术演示阶段不要进入报价。回复："在确认技术方案能跑通之前谈价格对你们不公平。我们先把验证范围定下来。" |

## 九、POC / 小范围验证模板

**原则：验证不是免费试用。** 它是一次有明确通过标准的评估，通过或未通过都是有效结论。

```markdown
# 小范围验证方案：[客户名称]

## 一句话问题陈述
本次验证将证明：集成中台能够在 [客户环境] 中完成 [具体链路]，
在 [时间范围] 内达成 [可测量标准]。

## 通过标准（开始前必须书面确认，双方签字或邮件确认）
| 编号 | 验证项 | 目标 | 测量方式 |
|---|---|---|---|
| C1 | 数据库 → 数据库 增量同步 | 数据一致，重复执行不产生重复数据 | 比对源/目标行数与关键字段 |
| C2 | 某 HTTP 接口 → 数据库 抽取 | 字段映射正确率 100% | 随机抽查 N 条记录逐字段核对 |
| C3 | 异常数据处理 | 失败数据进入死信区可修正后重新落库 | 人为构造脏数据，走完整流程 |
| C4 | 可观测 | 执行记录可定位失败步骤；指标可被抓取 | 展示执行详情与指标接口 |
| C5 | （按客户场景增补） | | |

## 范围 —— 明确做什么，也明确不做什么
**范围内**：上述 C1–C4 涉及的连接器、任务配置、死信与审计能力
**范围外（并说明原因）**：
- 变更数据捕获（CDC）—— 产品当前不提供
- 与客户生产环境的网络打通以外的性能压测
- 第一阶段不涉及的可视化深度定制
- 新增需求统一进入第二阶段评估

## 时间安排
- 第 1–2 天：环境就绪、数据源登记与测连
- 第 3–7 天：核心链路配置、映射预览、试跑
- 第 8 天：**中期复盘**（确认进度、确认标准未变更）
- 第 9–12 天：异常场景验证（死信、重试、回滚）
- 第 13–14 天：结果整理与决策会

## 决策点
第 14 天召开决策会，基于上述通过标准给出 GO / NO-GO 结论。
```

**两个必须守住的纪律**：

1. **中期复盘不能省**。如果客户在验证中途调整标准，没有中期复盘你会在最后一天才发现。
2. **范围蔓延要当场挡回**。"这个也能测吗？"——"可以，放到第二阶段。我们先把核心链路跑出明确结论。"

## 十、演示前 48 小时检查清单

**环境**
- [ ] 数据库、后端服务、控制台全部启动并验证登录
- [ ] 演示环境数据已重置为干净状态（不要复用上次演示的脏数据）
- [ ] 确认演示机器的网络能访问所有需要的数据源
- [ ] 关闭所有无关的通知弹窗、聊天软件、浏览器多余标签页

**数据与内容**
- [ ] 准备一条**故意失败**的脏数据，并确认它能稳定触发失败
- [ ] 准备一条已成功跑完的同步链路（用于 Impact-First 的"先看结果"）
- [ ] 确认映射预览能展示有意义的字段差异
- [ ] 安全清单已打印（**纸质**，用于现场推到桌子中间）

**风险预案**
- [ ] 每个关键演示步骤都有截图或录屏作为后备
- [ ] 如果现场网络不可用，有本地可运行的演示路径
- [ ] 想清楚"如果被问到 CDC / K8s / 大文件传输"的标准回答（见第八节）

**听众**
- [ ] 确认参会名单与角色（技术评估 / 业务决策 / 安全 / 采购）
- [ ] 根据角色选定主线（第六节的角色映射）
- [ ] 准备一条与客户同行业的参照场景

**收尾**
- [ ] 明确下一步是什么、谁来做、什么时候
- [ ] 确认会议结束时能拿到一个具体承诺（哪怕只是"下周把安全清单反馈给我们"）

## 十一、演示后 24 小时跟进

1. **当天**：发一封简短邮件，包含三样东西——本次结论一句话、待办事项与负责人、附件（本次演示稿 + 安全能力清单）。
2. **附上录屏**。如果演示中有现场操作，附上完整录屏，方便对方内部转述。这是最高性价比的资产。
3. **不要问"你们考虑得怎么样"**。改为给出一个有时间和动作的提议："按今天的结论，建议下周完成一次针对 XX 链路的环境确认，我方负责准备环境检查清单。"

演示前问自己三件事：

演示后必做三件事：
  · 24 小时内发结论 + 附件 + 录屏

  · 把新学到的客户信息补进评估记录
